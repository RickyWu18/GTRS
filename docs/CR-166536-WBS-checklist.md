### ▸ 影像存放已定案：方案甲 ＋ Git LFS

影像與資料同 repo，`scans/*.webp` 以 LFS 追蹤，使影像物件不進入一般 git 歷史。

**必須先解決的相容性問題：GitHub Pages 不提供 LFS 檔案。** Pages 會回傳約一百多位元組的 pointer 文字檔而非影像，F3 掃描對照將完全失效。這不是設定問題，GitHub 官方文件明列此限制且無支援計畫。採用路徑為改以 GitHub Actions 部署 Pages（見 W1.2）。

**三點實務注意**

1. **配額。** Free/Pro 帳號目前含 10 GiB 儲存與每月 10 GiB 頻寬（未遷移至計量計費之帳號為 1 GiB）。本專案全本 25–45 MB，即使每次 push 都拉取，1 GiB 亦可支撐約 20 次以上建置。
2. **貢獻者門檻。** 協作者需執行 `git lfs install`，否則取得 pointer 檔。此為 4.3「降低協作門檻」的小幅退讓，須寫入 W4.0 之 SOP。
3. **收益在本專案量級上有限。** 5.8.3 已載明「體積並非本專案的實際約束」——即使重轉三次，歷史累積亦僅約一百餘 MB。LFS 買到的是保險，代價是 5 h 增量與部署路徑複雜化。

**新增風險 R15　LFS 與 Pages 不相容導致掃描對照失效**（影響：高）。應對：W1.2 於批次轉檔前實測，通過方可進入 W1.3；未通過則退回純方案甲，此時無沉沒成本。

**#6 的理由。** 三點：

1. **手寫不是原文。** 5.3 的 `latex`／`text.en` 定義為 Ferguson 原文的忠實轉錄。手寫是後人在某一份影本上所加，寫的人不明。
2. **資訊不會遺失。** F3 掃描對照呈現原始頁面影像，手寫仍然看得到。`scans/` 是權威物件，YAML 是打字報告的轉錄。
3. **實測為冗餘而非補漏。** W1.4 唯一發現的實質案例 pdf 333，其手寫填的是 `K_1`–`K_3` 的數值，而該三者已由 pdf 324（A-256）正式宣告為 subsystem 18 之 Coefficients，權威數值應在附錄 C。手寫沒有補上原文缺漏的東西。

連帶：W2.2 少一項待決事項，schema 不需新增 `annotations` 類欄位。日後若遇到手寫**確實補上了原文缺漏**的案例（例如原文未宣告的符號），本決議應重新檢視。

**#8 的理由。** 失效模式是靜默的，這是關鍵。雙引號下漏寫一個反斜線不會報錯，只會把
`\beta_m` 變成退格字元加 `eta_m`，而 F1／F2 建立在字串完全相等的比對上——該符號
從此永遠比不中，且沒有任何錯誤訊息。單引號不處理跳脫，轉錄者寫什麼就是什麼。
代價是單引號內的撇號須連寫兩個（`\Omega'_R` → `'\Omega''_R'`），但撇號在本文件中
遠少於反斜線。規約全文與實測結果見 `data/symbols.yaml` 檔首；`equations/*.yaml`
的 `latex` 欄位同樣適用，須寫入 W4.0 的 SOP。

**#9 的理由。** 先確認這不屬於「為消歧而造原文沒有的 key」——**原文自己就以豎線
區分**這兩個量，編碼該區分是忠實轉錄而非發明。以 subsystem 9 為例，`SL_CG` 是輸出
變數、`SL_CG|_{\beta_m=0}` 是輸入常數，同章並列，不區分則該章自身即衝突。

`_at_` 的選法與既有的重音規則同型：`\dot{p}` → `p_dot` 是「把標記轉成字尾詞」，
豎線 → `_at_` 是同一作法，且讀得出來。另兩個候選各有問題：`SL_CG_beta_m_0`
與真的帶下標 `\beta_m` 的符號無法區分；`SL_CG_vert_beta_m_0` 的 `vert` 既非原文
用語，`\big` 也只是尺寸巨集而非內容。

**#9 的擴充（同日）。** 初版僅依 subsystem 9 的 6 個實例定案，兩章之後即不敷使用——
subsystem 2 的豎線帶座標系上標與斜線下標（`U_i|^B_{R/WL}`），語意是「限定符」而非
「求值條件」，12 筆因此標了 `schema_gap`。經 44 頁符號欄取樣調查後改為**機械規則、
不區分語意**：需要判斷語意的規則會被判錯，而判錯不會報錯。

此處的教訓是規約不該從單一章節推導。初版定案時只看過一章，擴充版本則以橫跨
24 個 subsystem 的取樣為依據。

**#10 的理由。** 元組是取捨，不是兩全。展開確實改寫了原文「一列」的呈現結構，但
不展開的代價是 F1／F2 對 subsystem 10a／10b／12／13／14 全面失效——那幾章的符號表
幾乎整頁都是 `(X,Y,Z)_F` 這種形式，而公式中出現的是單一分量 `X_F`，永遠比不中。

展開屬機械操作（依逗號切分，共同下標分配至各分量），不涉語意判斷；原文的並列形式
由各筆的 `notes` 保存，資訊不遺失。

**#13 的實作條件與限制。** 三點，皆為暫不實作的理由：

1. **須以 W2.6 的 loader 為基礎，不另寫一套。** 覆核頁面要做的兩件事——載入 YAML、
   渲染 LaTeX——正是 W2.6 與 W2.7 的職責。在其之前實作會產生兩份會分岔的程式，
   而 W2.6 的判準（遇未定義欄位靜默略過）等行為必須統一。
2. **站台版與離線版的資料來源應不同。** 離線版把資料內嵌，是因為 Chrome 擋
   `file://` 的 fetch；站台版應以 js-yaml 於執行期載入（`index.html` 已如此載入
   js-yaml 與 KaTeX），資料才會永遠是最新的，也才符合 4.3「純前端無建置流程、
   commit 即生效」。
3. **純靜態站台寫不回 repo。** 貢獻者只能匯出 JSON 後另行提交（PR 或寄送），
   迴路不會自動閉合。若要閉合需接 GitHub API，那是另一個層級的變更。

實作時應置於外殼層（`js/app.js` 那一層，4.2 允許自由變更），不得寫入凍結的
`js/render/`。

**#14 的理由。** 案例是 7A（pdf 176）與 7B（pdf 188）的 LANDING GEAR LOCATIONS
三式，**逐字相同**。W2.2 初測時預期 `supersedes`——因為 7B 章名標 Unused Bell
Model，看起來是被取代的舊模型。實測後改判：

1. **式子本身沒有新舊。** `X_n = SL_{CG} - SL_{G_n}` 在兩章是同一行字。標
   `supersedes` 會宣稱「7A 的式子取代了 7B 的式子」，那是對原文的詮釋，不是原文
   說的——原文說的是「這一章的模型未使用」，範圍是整章。依 CLAUDE.md
   「不重新推導或修正原文」，詮釋不下放到式子層級。
2. **單向即足夠，且不應要求雙向。** `same_as` 語意對稱，但若 schema 要求雙向，
   `relates_to` 就變成必須成對維護的欄位——漏一邊不會報錯，只會靜默少一條連結，
   正是規則 3 所述「本專案最難察覺的失效模式」。改由渲染層自建反向索引，
   維護成本落在程式而非資料。記入 W2.8 的實作要求。
3. **`expands`／`simplifies`／`supersedes` 仍無真實案例。** 值域是否夠用要到 P4
   大量轉錄後才知道。三者皆為同一欄位的不同值，日後增減不構成破壞性變更。
