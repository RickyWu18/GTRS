## 1. 專案概述

### 1.1 背景

NASA CR-166536 是 NASA Ames 研究中心垂直運動模擬器（Vertical Motion Simulator, VMS）上通用傾轉旋翼模擬程式（GTRSIM）的數學模型文件，由 Bell Helicopter 的 S. W. Ferguson 於 1988 年撰寫。該報告至今仍是傾轉旋翼飛行動力學建模領域被引用最頻繁的基礎文獻之一。

文件本身為 1988 年產出的掃描 PDF，約 300 餘頁，檔案大小超過 30 MB，無文字層（待確認）。內容包含各次系統的數學模型推導、模組間的耦合關係，以及大量以 XV-15 為基礎的幾何、慣量與氣動係數資料表。

### 1.2 問題陳述

原始文件以掃描影像形式存在，導致三個實際障礙：

- **無法全文檢索。** 符號在前段定義、在後段使用，查閱需反覆翻頁。
- **公式無法引用。** 無法複製、無法交叉連結、無法在其他文件中重用。
- **系統耦合關係隱含於文字之中。** 模組之間的訊號流向散布在各章節敘述裡，沒有整體性的呈現。

### 1.3 授權狀態

NASA Contractor Report 一般標示為 "Work of the US Gov. Public Use Permitted."，數位化、重製與公開發布無授權疑慮。

惟本報告係由 Bell Helicopter 之承包商人員撰寫，承包商著作並非自動構成美國政府著作。M0 階段應直接查驗以下三項，並以一手證據取代本節之通則引述：

- 封面／內頁之 distribution statement 與有無 Bell 之版權標記
- 圖表是否有轉載自第三方之來源標註
- NASA 公開發布頁面所載之使用條款

實務風險評估為低（文件已由 NASA 公開站台長期提供下載），但既然成本僅為翻閱封面，不宜以推定代替查證。

## 2. 目標與非目標

### 2.1 主要目標

建立一個可全文檢索、可交叉追溯的靜態網站，使讀者能有效率地**理解**此數學模型，消除原始 PDF 的查閱摩擦。

### 2.2 次要目標

該網站同時作為團隊共用的技術參考資源，可經由版本控制協作修正、逐步擴充。

### 2.3 明確排除項目

- **不實作模擬器。** 本專案不產出 MATLAB/Simulink 或 Python 的可執行模型。
- **不進行數值驗證。** 由於不實作模擬器，無法以配平計算反向驗證公式轉錄的正確性。此限制對品保設計有決定性影響，詳見第 9 節。
- **不重新推導或修正原文。** 原文若有錯漏，以註記方式標示，不逕行更改。

### 2.4 目標的天花板在原文本身

後續研究者曾公開指出，僅憑 CR-166536 無法完整重現 Ferguson 的模型，原因是原文缺乏完整的數學推導描述，且部分變數定義不清（見 McVicar 1993、Barra 等後續文獻）。

此事實對本專案有兩層意涵：

1. **「讀懂模型」的上限不由數位化品質決定。** 即使轉錄百分之百正確，仍會存在原文未交代的推導跳步與未定義符號。本專案不承諾補上這些缺口。
2. **原文的不完整之處應被系統性標記，而非默默略過。** 這反而是本專案最具價值的副產品之一：`issues` 之 `undefined_in_source` 型別與 `symbols.yaml` 之 `source: inferred` 共同構成一份「原文哪裡講不清楚」的清單（見 5.3、5.4）。此清單在原始 PDF 中不存在，且對後續實作者的價值可能高於公式轉錄本身。

## 4. 系統架構

### 4.1 核心原則：內容與呈現解耦

本專案最重要的架構決策是：**內容渲染層寫一次即凍結，之後所有內容工作僅為向資料目錄新增檔案。**

```
掃描頁 ──OCR/轉錄──▶ 結構化資料層 ──▶ ┌─ 靜態網站
                        (YAML/CSV)      ├─ 相依關係圖（自動生成）
                                        └─ 全文檢索索引（自動生成）
```

此設計的理由在於專案規模。全本數位化是數週至數月的長期工程，若採取「一邊 OCR 一邊撰寫 HTML」的做法，在累積數十頁後將面臨公式編號錯亂、符號定義散落、變數更名需全站搜尋等問題，實務上會導致專案中止。

解耦後，任何時間點停工，已完成部分皆為可用成品。

### 4.2 「凍結」的範圍界定

須凍結的僅為**渲染層**，非全部前端程式碼。兩者區分如下：

| 層級 | 凍結狀態 | 內容 | 變更成本 |
|---|---|---|---|
| **渲染層** | 凍結 | 公式渲染、符號提示、交叉追溯、檢索、掃描對照 | 高——與資料 schema 綁定，變更需回頭修改全部 YAML |
| **外殼層** | 自由變更 | 首頁、導覽、版面配置、配色、排版、字體 | 低——與資料 schema 無關 |

專案期間隨時可重新設計首頁與視覺，不影響已完成的內容。

外殼層的實作方式**不設限制**——首頁可為手寫 HTML、可資料驅動、可依需求改以任何方式組裝，皆屬合理選擇。此處刻意不預先規定，以免在需求尚未明朗前限縮設計空間。

為確保上述彈性成立，僅需遵守兩項約束，兩者均落在渲染層與樣式層，不影響外殼層自由度：

**約束一：設計代幣集中管理。**
`css/tokens.css` 集中定義色彩、字級、間距、圓角等變數。視覺調整不觸及結構。

**約束二：渲染層僅暴露函式，不決定佈局。**
渲染層對外介面為 `renderEquation(eq) → HTMLElement` 形式，由外殼層決定置於何處、如何排列。渲染層不得寫入版面相關的 CSS class 或容器結構。

**約束三：渲染層必須忽略不認識的欄位。**
載入 YAML 時遇到 schema 未定義的欄位，一律靜默略過，不得報錯或中止。此規則使「日後新增選填欄位」永遠不構成破壞性變更——舊資料照常運作，新資料在舊版渲染層下僅少顯示一項資訊。`meta.yaml` 另設 `schema_version`，僅在真正發生破壞性變更時遞增，屆時可據以撰寫遷移腳本。

M1 階段建議先實作最簡首頁（章節列表加檢索框）。待首頁設計確定後可完全重寫，不造成返工。

### 4.2.1 凍結的標的是 schema，不是程式碼行數

須釐清「凍結」實際保護的對象。**渲染層的程式碼可以繼續增補，真正不可輕易變動的是資料 schema 與渲染層的對外介面。** 因此：

- 為 `render/table.js` 增加排序與繪圖能力（F8）**不違反凍結**，因為它不要求任何 YAML 回填。
- 為公式新增一個必填欄位**違反凍結**，因為它要求回頭修改全部既有檔案。

判斷準則只有一條：**該變更是否要求回填既有資料？** 若否，隨時可做。

### 4.2.2 真正昂貴的是「事後推不出來」的資訊

回填成本並非一律相同，取決於資訊性質：

| 資訊性質 | 現在就留欄位 | 理由 |
|---|---|---|
| 看原文才知道、事後由 YAML 推不出（跨頁、方程組歸屬、原文未定義、改寫關係） | **是**，可全部留空 | 回填必須重開掃描頁重讀原文 |
| 可由既有欄位推導（交叉引用、被引用次數、章節排序） | **否**，永遠不另存 | 存了就會與來源不同步 |
| 純顯示格式（括號處理、編號正規化） | 隨時可加 | 腳本批次處理即可 |

第一類欄位已於 5.3、5.4 一次補齊。

### 4.2.3 凍結前的 schema 壓力測試

M1 若僅以「中等難度章節」驗證，將以最不具代表性的樣本決定凍結內容——旋翼、混控邏輯、短艙傾轉排程等最可能撐爆資料模型的內容都排在 M3 之後。

因此 **M1 須額外抽取 3–5 頁旋翼與飛行控制章節的公式灌入 schema**，僅驗證表達力，不做完整轉錄。重點檢查：分段／條件式、方程組、矩陣與向量式、跨頁續行式、同一量在不同章節的改寫版本。

### 4.2.4 殘餘風險的止血機制

即便如此，仍不可能預見全部結構。轉錄者遇到 schema 裝不下的資訊時，就地留下標記而非略過：

```yaml
issues:
  - kind: schema_gap
    note: "此式續至次頁；目前無欄位可記錄其續行範圍"
```

日後補上欄位時，不需重讀全本，只需檢索 `schema_gap` 回頭處理該數條。此舉將回填成本由「全本規模」降為「標記數規模」，是本問題唯一務實的止血手段。

須注意：`status` 機制**不能**替代此機制。狀態標記保證的是「抄對」，不保證「抄全」——一條跨頁公式可以是 `verified`（內容確實逐字核對無誤），但若當時 schema 無處記錄其跨頁事實，該資訊仍然遺失。兩者處理的是不同軸向。

### 4.3 為何不使用建置流程

在純前端限制下，資料層採用 YAML 並於瀏覽器端以 js-yaml 解析。此選擇使得：

- 貢獻者手寫的是人類友善格式，非 JSON
- 新增一章內容不需執行任何指令，直接 commit 即生效
- 降低協作門檻，非開發背景的成員亦可參與校對

代價是首次載入需解析數個 YAML 檔案。以本專案的資料量級（預估總計數 MB）此成本可接受，必要時可改為分章延遲載入。

### 5.2 頁碼對照（meta.yaml）

1988 年報告的頁碼編號並非單一連續數列。除正文的阿拉伯數字外，前言常用羅馬數字，附錄則多採 `A-1`、`B-12` 形式的複合編碼。頁碼模型須能同時容納三者，並與 PDF 實體頁碼建立對應。

```yaml
schema_version: 1          # 僅於破壞性變更時遞增（見 4.2 約束三）

document:
  id: CR-166536
  title: A Mathematical Model for Real Time Flight Simulation of a Generic Tilt-Rotor Aircraft
  author: Ferguson, S. W.
  year: 1988
  source_url: https://rotorcraft.arc.nasa.gov/Publications/files/CR-166536_882.pdf

page_map:
  - kind: front_matter
    label_format: roman          # i, ii, iii …
    pdf_start: 1
    count: 14
  - kind: body
    label_format: arabic         # 1, 2, 3 …
    pdf_start: 15
    count: 240
  - kind: appendix
    label_prefix: "A-"           # A-1, A-2 …
    label_format: arabic
    pdf_start: 255
    count: 40
  - kind: appendix
    label_prefix: "B-"
    label_format: arabic
    pdf_start: 295
    count: 25
```

**衍生規則（適用於全部資料檔）**

1. **雙欄位並存。** 每筆引用同時記錄 `pdf_page`（整數）與 `printed_page`（字串）。
2. **排序、導覽、影像檔名一律使用 `pdf_page`。** 因附錄編碼無法正確排序，混用將導致上下頁跳頁錯亂。
3. **顯示一律使用 `printed_page`。** 讀者對照紙本或原 PDF 內文時，看到的是印刷頁碼。
4. **`printed_page` 必須為字串型別。** 寫成 `A-12` 而非 `A12` 或數字。YAML 中未加引號的 `A-12` 仍會被解析為字串，但建議明確加引號以免歧義。
5. **公式與圖表編號同樣可能為複合格式**（`(A-3)`、`Figure B-7`）。`original_number` 欄位一律以字串處理，不得假設為數字。

### 5.3 公式定義（equations/*.yaml）

#### 5.3.1 基本型（絕大多數公式僅需這些欄位）

```yaml
- id: eq-rotor-4-12
  module: rotor
  section: "4.3.2"
  kind: single                       # single | piecewise | system | definition
  pdf_page: 101                      # 整數，主定位，用於排序與取圖
  printed_page: "87"                 # 字串，可為 "A-12"
  latex: "T_R = \\rho A_R (\\Omega R)^2 C_T"
  lhs: [T_R]
  rhs: [rho, A_R, Omega, R, C_T]
  original_number: "(4-12)"          # 字串，可為 "(A-3)"
  text:
    en: "The rotor thrust is computed from …"   # 原文轉錄（權威）
    zh: "旋翼推力由…計算得出"                      # 該段原文之對譯（非權威，見 5.7.2）
  status: verified                   # draft | reviewed | verified
  issues: []
  bbox:                              # 選填，見下方說明
    - {page: 101, rect: [0.18, 0.34, 0.72, 0.41]}
```

日常轉錄工作九成以上只會接觸 `id / latex / lhs / rhs / pdf_page / status` 六個欄位。以下的擴充欄位皆為選填，僅於遇到對應結構時才使用——**規格的複雜度落在文件上，不落在日常填寫上。**

#### 5.3.2 擴充欄位（選填）

**`kind`　結構型別**

`latex` 永遠是一條完整可渲染的字串，渲染層只吃這個欄位；`kind` 供檢索、檢查腳本與統計使用。

**`condition_symbols`　分段式的條件符號**

分段函數以 `\begin{cases}` 寫在單一 `latex` 字串內，但**只出現於條件式中的符號必須與 `rhs` 分開存放**：

```yaml
  kind: piecewise
  latex: "C_L = \\begin{cases} a_0\\alpha & \\alpha \\le \\alpha_s \\\\ \\dots \\end{cases}"
  lhs: [C_L_w]
  rhs: [a_0, alpha_w]                # 主體符號
  condition_symbols: [alpha_stall]   # 僅為分段門檻，非自變數
```

若混入 `rhs`，F2 的「被哪些公式使用」會把失速攻角誤報為升力係數的自變數。

**`group`　方程組歸屬**

六自由度運動方程等成組出現者，**採平坦多筆加 group 標記，不使用巢狀結構**：

```yaml
  group:
    id: grp-eom-6dof
    title_en: Body-axis force equations
    order: 2
```

理由：F9 要求每式具備獨立永久 URL，`status` 與 `issues` 亦應能逐式標記；巢狀會迫使 loader、檢索與路由全部處理兩層結構。

**`pdf_pages`　跨頁續行**

`pdf_page` 維持整數作為主定位（排序依據不變），跨頁時另記：

```yaml
  pdf_page: 101
  pdf_pages: [101, 102]
```

**`shape`　`scalar | vector | matrix`**

矩陣與向量式不需要新結構，KaTeX 直接支援 `\begin{bmatrix}`。此欄位僅用於讓檢查腳本將矩陣式標記為 skipped 而非誤判。

**`relates_to`　原文改寫關係**

同一物理量在不同章節以不同形式出現時（本報告幾乎確定會有）：

```yaml
  relates_to:
    - kind: expands | simplifies | supersedes | same_as
      target: eq-rotor-4-5
```

#### 5.3.3 `issues` 型別化

`issues` 不再是自由文字陣列，改採型別化結構。此變更成本近乎零，收益顯著：

```yaml
  issues:
    - kind: undefined_in_source      # 原文從未給出定義
      symbol: k_1
      note: "依 4.2 節上下文推測為經驗修正係數"
    - kind: illegible                # 掃描不清，無法判讀
    - kind: suspected_typo           # 疑為原文誤植
    - kind: cross_page               # 跨頁且銜接處不明
    - kind: ocr_uncertain            # 機器辨識信心低，待人工確認
    - kind: schema_gap               # schema 裝不下之資訊（見 4.2.4）
```

型別化後，M6 可自動彙整「原文未定義符號清單」（見 2.4），F11 可依型別分類顯示，`schema_gap` 可被檢索用於日後回填。

#### 5.3.4 關於 bbox 的定位與成本

bbox 的用途是**顯示裁切**：讀者點選「對照原文」時，前端載入整頁影像並以 CSS 裁切至該公式所在區域，不需另存裁切檔。次要用途為反向導覽的錨點（在掃描頁上疊加標示框）。

**格式一律為 list，即使僅有一項。** 每項含 `page` 與相對座標 `rect`，如此跨頁公式無需另立 schema：

```yaml
  bbox:
    - {page: 101, rect: [0.18, 0.72, 0.72, 0.88]}
    - {page: 102, rect: [0.18, 0.10, 0.72, 0.19]}
```

座標採相對值 `[x1, y1, x2, y2]`，原點為頁面左上。**相對座標與影像解析度無關，DPI 變更不需換算**；真正會使座標失效的是裁邊（crop）、去歪斜（deskew）與旋轉，故此三項必須與 DPI 一併於 M0 定案（見 5.8.7）。

不為每條公式產生獨立影像檔的理由：全本預估數百至上千條公式，逐一裁圖將產生同等數量的檔案，且框選錯誤需重新產生。記錄座標則修正僅需更動四個數字。

此欄位的成本完全取決於取得方式：

| 取得方式 | 成本 | 建議 |
|---|---|---|
| 版面偵測工具自動輸出（見 7.1） | 趨近於零，為 OCR 副產品 | 記錄保存 |
| 人工框選 | 每條約 1 分鐘，全本 8–10 小時 | 不建議投入 |

因此 **bbox 為選填欄位**，前端須支援優雅降級：

- 有 bbox → 裁切顯示該區域，並提供「檢視整頁」切換
- 無 bbox → 顯示整頁影像，依 `pdf_page` 定位

此設計使專案不因座標未標註而阻塞。可先全數留空上線，日後由 OCR 管線批次回填。實務上最終多為混合狀態（自動偵測成功者有座標，失敗者無），屬可接受情形。

### 5.4 符號字典（symbols.yaml）

此為整個專案的基礎設施。1988 年掃描件的 OCR 極易將 `α` 誤判為 `a`、將帶上標的符號誤判為雜訊；若無預先建立的符號字典，這類錯誤在校對時無從發現。

```yaml
- key: C_T
  scope: rotor                       # subsystem id，或 global
  latex: "C_T"
  name_en: thrust coefficient
  name_zh: 推力係數
  units: "—"                         # 顯示用
  dimension: {}                      # 選填，機器可讀（無因次以空物件表示）
  source: nomenclature               # nomenclature | inline | inferred
  defined_in: eq-rotor-4-5
  fortran: "CT"                      # 對應 CR-166535 之變數名
  notes: "以旋翼盤面積與槳尖速度無因次化"
```

`fortran` 欄位用於與姊妹文件 CR-166535（Programmer's Guide）交叉對照。該指南載有副程式呼叫架構與 COMMON block 變數清單，是理解模組串聯關係最直接的來源。

#### 5.4.1 `scope`：符號的命名空間

**原文並無全書統一的符號表，而是各 subsystem 章節各附一份。** 此結構直接決定資料模型：`scope` 不是本專案發明的分類，而是照抄原文的組織方式。

其必要性在於符號重名。300 頁的報告中 `T`、`V`、`a`、`S`、`q` 在不同 subsystem 指涉不同物理量，幾乎是必然。若採全域平坦命名空間，將被迫造出 `T_rotor`、`T_engine` 這類**原文從未出現的人工 key**，讀者在公式中看到的符號與字典中的鍵值因而對不起來。

有了 scope，兩張表各自照實記錄即可，不需消歧。

**解析規則（屬渲染層，凍結範圍內）**

查詢某公式中的符號時：

1. 先在該公式所屬 `module` 對應的 scope 中尋找
2. 找不到則退回 `scope: global`
3. 仍找不到 → 視為未定義符號，由檢查腳本報錯（見 9.2）

耦合變數（`w_i`、`V_inf`、大氣常數、機體狀態量）會跨多個 subsystem 出現且措辭可能略有出入，一律歸入 `global`，於 M2 統一裁定。

#### 5.4.2 key 命名規約

F1 與 F2 完全建立在**字串完全相等**的比對上。命名不一致不會產生任何錯誤訊息，只會靜默地少掉一條交叉引用——這是本專案最難察覺的失效模式，故命名規則必須明文化。

**規約：一律採 LaTeX 風格，去除反斜線與大括號。**

| 原文符號 | key | 說明 |
|---|---|---|
| $C_T$ | `C_T` | 下標以底線連接 |
| $\rho$ | `rho` | 希臘字母用 LaTeX 名稱，去反斜線 |
| $\Omega$ | `Omega` | 大寫希臘字母首字母大寫 |
| $\alpha_s$ | `alpha_s` | |
| $\theta_{75}$ | `theta_75` | 去除大括號 |
| $\beta_{1c}$ | `beta_1c` | |
| $\dot{p}$ | `p_dot` | 重音置於字尾 |
| $\bar{c}$ | `c_bar` | |
| $V_\infty$ | `V_inf` | `\infty` 縮寫為 `inf` |

補充規則：

- 大小寫具意義，不得正規化（`R` 與 `r` 為不同符號）
- 多層下標以底線串接，順序照原文由左至右（$C_{L_w}$ → `C_L_w`）
- 禁止為消歧而造原文沒有的 key，消歧一律交由 `scope` 處理

`latex` 欄位保存該符號的完整 LaTeX 寫法，是 F1 比對的實際依據（見 6.1）。

#### 5.4.3 `source`：符號定義的來源

| 值 | 意義 |
|---|---|
| `nomenclature` | 原文之 subsystem 符號表列出 |
| `inline` | 原文正文中定義 |
| `inferred` | **原文從未定義**，由轉錄者依上下文推測 |

`inferred` 直接對應 `issues.kind: undefined_in_source`（見 5.3.3），兩者應相互校驗。此類符號的數量與分布本身即為有價值的產出（見 2.4）。

#### 5.4.4 `dimension`：選填

`units` 供人閱讀，`dimension` 供程式檢查，兩者並存：

```yaml
  units: "slug/ft^3"
  dimension: {M: 1, L: -3}
  is_angle: false                    # 角度量綱上無因次，但三角函數引數檢查需區辨
```

此欄位**不強制填寫**。量綱檢查已由 v1.2 降為選配（見 9.2），保留欄位的成本近乎零，能填則填即可。

  chapter: 4

  outputs: [T_R, H_R, Y_R, Q_R, M_R, w_i]

### 5.6 附錄資料的三種型態

附錄內容不應以單一模型處理。依結構性質分為三類，各有專屬存放方式：

| 型態 | 存放位置 | 資料模型 | 說明 |
|---|---|---|---|
| 常數表 | `data/constants.yaml` | 鍵值對 | 單一數值，如旋翼半徑、空機重量、慣量 |
| 多維查表 | `data/tables/*.csv` | 表格 | 如 C_L 對 α 與 Mach 之函數關係 |
| 曲線圖 | `scans/` + `figures/*.meta.yaml` | 影像 | 僅有圖形，無數值；選擇性數化 |

#### 5.6.1 多維查表（tables/）

數值資料以 CSV 保存，附帶 `*.meta.yaml` 描述欄位意義、單位與來源頁碼。此格式使表格可直接於網頁渲染為可排序表格或曲線圖，亦便於他人下載重用。

```yaml
# A3-cl-alpha.meta.yaml
id: table-A3
title_en: Wing lift coefficient vs angle of attack
title_zh: 機翼升力係數對攻角
pdf_page: 268
printed_page: "A-14"
columns:
  - key: alpha
    symbol: alpha_w
    units: deg
  - key: mach
    units: "—"
  - key: cl
    symbol: C_L_w
    units: "—"
status: draft
```

#### 5.6.2 常數表（constants.yaml）

常數表結構最單純，成本最低，已涵蓋於工時估算內。但**不應存放於 `tables/`**——它並非表格資料，而是鍵值對，混入表格模型將使查詢與交叉連結變得繁瑣。

```yaml
- symbol: R
  value: 12.5
  units: "ft"
  name_en: rotor radius
  name_zh: 旋翼半徑
  pdf_page: 256
  printed_page: "A-2"
  applies_to: [XV-15]
  status: reviewed
```

**此設計的關鍵價值在於與符號提示（F1）串接。** 讀者在正文公式中查詢符號 `R` 時，除定義與單位外，可同時顯示「= 12.5 ft（XV-15）」。此舉將附錄數據與正文推導縫合為單一閱讀體驗，是本專案「讀懂模型」目標的重要組成，且幾乎不增加額外工時——僅為將資料置於正確結構。

`applies_to` 欄位保留機型維度。若原文同時列出多組構型的數值，可並列多筆而不衝突。

#### 5.6.3 曲線圖

處理策略詳見第 10 節。預設僅保存掃描影像，不進行數值化。

### 5.7 雙語內容模型

#### 5.7.1 基本原則：英文為史料，中文為註解

兩種語言在本專案中**地位不對等**，不應以一般 i18n 的對稱方式處理：

- **英文** 為 Ferguson 原文的忠實轉錄，具權威性，是引用與驗證的依據
- **中文** 為理解性譯註，不具權威性，可能包含轉譯過程的詮釋

此區別必須在資料結構與視覺呈現上同時體現。

#### 5.7.2 結構

中文內容有兩個存放位置，**兩者職責不同，不得混用**。v1.1 對兩處均稱「譯註」，語意重疊，此處明確切分：

| 位置 | 內容性質 | 判準 |
|---|---|---|
| `text.zh`（見 5.3） | **該段原文的對譯** | 原文有這句話，只是換成中文。不得增添原文未載之內容 |
| `notes/zh-TW/*.md` | **譯者的補充說明** | 原文沒有這句話，是為幫助理解而寫的背景、推導補述、與他處的關聯 |

判斷方式很單純：**若刪去這段文字會使原文的意思缺一塊，它屬於 `text.zh`；若刪去只是少了幫助，它屬於 `notes/`。**

介面字串置於 `i18n/`，與上述兩者皆無關。

**嚴禁將中文理解寫入 `latex`、`text.en` 或 `note` 欄位。** 專案跨度數月，若兩者混雜，後期將無法區分何者為原文、何者為當時推測。

#### 5.7.3 顯示模式

提供三種切換：

| 模式 | 用途 |
|---|---|
| EN only | 引用、與原文核對 |
| ZH only | 快速閱讀 |
| 對照 | 段落交錯或並排，本專案主要使用情境 |

#### 5.7.4 術語處理規範

中譯術語首次出現時**必須併列英文原文**。傾轉旋翼領域的中文術語缺乏統一標準，例如「沉浸面積」一詞，讀者若無 immersed area 即無法檢索相關文獻。

實作上，`symbols.yaml` 之 `name_zh` 於渲染時一律採「中文（English）」格式，不需逐處手動標註。

### 5.8 掃描影像處理規格（**待決 — 由開發者於 M0 確認**）

> **決策狀態：未定。** 本節提供選項與風險分析，最終參數須由實際執行者在 M0 抽樣測試後決定，並將決定值回填本節。在參數定案前不得開始批次轉檔。

#### 5.8.1 為何此決策必須提前定案

影像參數具有**不可逆性**與**歷史累積性**：

- 掃描影像一旦 commit，即永久留存於 git 歷史。日後重新產生不會縮小 repo，只會使其膨脹。
- 若中途更換參數，全本將出現畫質不一致。bbox 採相對座標，**不因 DPI 變更而失效**，但裁邊、去歪斜與旋轉會使既有座標全部作廢，故此三項與 DPI 同樣須一次定案。
- 影像品質直接影響 OCR 準確率，而 OCR 是主要工時項目。參數選錯將在 M3 才顯現，屆時已投入大量工時。

**原則：參數先定，產生一次，不再重跑。**

#### 5.8.2 選項與取捨

| 方案 | 全本大小 | OCR 準確率 | 風險 |
|---|---|---|---|
| A. 二值化 + WebP 無損 | 6–12 MB | 通常最高 | 淡字可能消失（不可逆） |
| B. 灰階 200 DPI + WebP q80 | 25–45 MB | 高 | 無實質風險 |
| C. 灰階 150 DPI + WebP q80 | 15–25 MB | 中高 | 細節損失，小字可能糊化 |
| D. 分類處理（文字頁二值化、圖表頁灰階） | 10–20 MB | 最高 | 流程較複雜，需頁面分類邏輯 |

#### 5.8.3 決策風險告知

**選擇二值化（方案 A 或 D）的風險**

二值化將每像素由 8 bit 壓為 1 bit。1988 年打字機掃描件的灰階多為紙張泛黃、光照不均、CCD 雜訊所致，不承載原始資訊，移除後通常同時改善檔案大小與 OCR 表現。但以下情形會造成**不可逆的資訊損失**：

- 淡化的手寫上下標可能被閾值整個切除
- 污漬、摺痕、影印疊影會變為實心黑塊，可能覆蓋字元
- 半色調網點的照片或陰影圖會劣化為雜點
- 極細線條（座標軸、曲線）可能斷裂

**選擇灰階（方案 B 或 C）的風險**

無實質品質風險，代價僅為 repo 體積。以 GitHub Pages 的軟性上限（1 GB）衡量，即使方案 B 的 45 MB 亦有充分餘裕。**體積並非本專案的實際約束**，不應為節省空間而承擔畫質風險。

**解析度過低（方案 C）的風險**

150 DPI 對正文尚可，但對下標、上標、希臘字母的區辨力不足，將直接推高 OCR 錯誤率與人工校對工時。此代價通常高於所節省的儲存空間。

#### 5.8.4 建議預設值

在無其他資訊的情況下，建議自 **方案 B（灰階 200 DPI + WebP q80）** 起步，理由為零品質風險、流程單純、可立即開始。

若 M0 抽樣測試顯示二值化能顯著提升 OCR 準確率，再改採方案 D（分類處理），並依 5.8.5 之保護措施執行。

#### 5.8.5 若採用二值化之必要保護措施

1. **保留原始灰階母本**，存放於 git 以外的位置（本機或雲端硬碟），確保任何時候可重新產生。
2. **採自適應閾值演算法**（Sauvola 或 Niblack），不使用全域固定閾值。
3. **建立頁面分類邏輯**：計算灰階直方圖，雙峰分佈者二值化，分佈平緩者保留灰階。
4. **逐頁目視抽檢**，重點檢查含手寫符號、污損、圖表之頁面。
5. **例外清單**：將不適用二值化的頁碼明確列出，改以灰階處理並記錄於 `meta.yaml`。

#### 5.8.6 影像存放策略

實際約束並非 GitHub 的容量上限（Pages 軟性上限 1 GB，上述任一方案皆有充分餘裕），而是 **git 歷史的累積**。影像若重複產生並 commit，每個版本皆永久保存於歷史中。

建議採下列其一：

- **方案 甲**：影像與資料同 repo，但參數一次定案、絕不重跑（流程最簡單）
- **方案 乙**：影像置於**獨立 repo**，主 repo 僅含純文字資料，前端經 jsDelivr 等 CDN 取圖（主 repo 永久輕量，clone 快速）

若預期會有多次重轉，應選方案乙。

**更正（v1.2）：「置於同一 repo 的獨立 branch」無法達成隔離效果。** 同一 repo 的所有 branch 共用同一個 object database，clone 時仍會取得全部物件（除非使用 partial／blobless clone）。要真正使主 repo 保持輕量，只能採獨立 repo、Git LFS 或外部儲存三者之一。v1.1 於 5.1 與本節提及之 branch 做法應予捨棄。

#### 5.8.7 待回填欄位

開發者定案後，請於此處記錄實際採用值：

```yaml
scan_spec:
  method:            # binarize | grayscale | mixed
  dpi:
  format:            # webp-lossless | webp-q80 | ...
  binarize_algo:     # sauvola | niblack | none
  deskew:            # true | false  ← 影響 bbox，必須一次定案
  crop:              # none | auto-margin | fixed  ← 影響 bbox
  rotate:            # none | auto   ← 影響 bbox
  exceptions: []     # 採例外處理之頁碼
  decided_by:
  decided_on:
  master_location:   # 原始灰階母本存放位置
```

`deskew` / `crop` / `rotate` 三項於 v1.2 新增。這三者一旦於中途變更，全本既有 bbox 座標將全部作廢，其後果較 DPI 變更更嚴重（見 5.3.4、5.8.1）。

### 5.9 轉錄覆蓋率台帳（coverage.yaml）

`status` 記錄於公式與資料表層級，可回答「這條式子核對過了嗎」，但**無法回答「第 137 頁處理過了嗎」**。跨數月的專案若缺少頁層級台帳，漏頁不會被任何機制察覺——沒有公式的頁面與尚未處理的頁面在資料中看起來完全相同。

```yaml
- pdf_page: 137
  state: done                # untouched | in_progress | done | no_content
  equations: 4               # 該頁產出之公式數
  note: ""
```

`no_content` 用於封面、空白頁、純敘述頁，使其與 `untouched` 明確區分。台帳可由腳本依 `equations/*.yaml` 之 `pdf_page` 自動初始化，人工僅需補標 `no_content` 與進行中狀態。

此檔亦是進度呈現的資料來源：網站可直接顯示「已處理 182 / 319 頁」。

## 6. 網站功能規格

主要目標為「讀懂模型」，功能重心置於降低查閱摩擦，而非視覺表現。

### 6.1 必要功能

**F1　符號即時提示（最高優先）**
公式中每個符號可 hover（桌面）或 tap（行動裝置）顯示定義、單位與定義處連結。若 `constants.yaml` 中存有該符號的數值，一併顯示（如「R　旋翼半徑（rotor radius）　= 12.5 ft（XV-15）」），使附錄數據與正文推導在同一處呈現。

**實作方式（v1.2 變更，屬凍結範圍）**

v1.1 原訂「KaTeX 渲染後掃描 DOM 比對符號」，此路徑不可靠：KaTeX 會將 `C_T` 拆為 `mord` 與 `msupsub` 等多層 span，重音（`\dot`、`\bar`）與巢狀上下標會使 DOM 結構進一步分裂，由渲染結果反推原始符號極易失敗。

**改採來源字串標註：於載入時對 `latex` 字串進行取代，再交給 KaTeX 渲染。**

1. 以 `symbols.yaml` 之 `latex` 欄位建立比對表，依長度由長至短排序
2. 對公式的 `latex` 字串做**最長匹配**取代，包成 `\htmlData{sym=C_T}{C_T}`
3. 交由 KaTeX 渲染（需開啟 `trust` 選項以允許 `\htmlData`）
4. 渲染結果中帶 `data-sym` 屬性的元素即為互動掛載點

此方案的優點：

- **轉錄者永遠只寫乾淨的 LaTeX**，不需在轉錄時手動標註，OCR 產出亦不需後處理
- 比對發生在字串層而非 DOM 層，行為可預測、可測試
- 純前端、無建置流程，符合 4.3 之限制
- 使 `symbols.yaml` 的 `latex` 欄位具備明確用途

實作須注意兩處陷阱：取代時必須避開巨集名稱（`\rho` 中的 `rho` 不得被誤取代）與 `\text{}` 內容。作法為先以正規表示式切出巨集與文字區塊並加以保護，僅對其餘部分執行取代。

**此為最高優先功能，須於 M1 最先驗證**——若此路徑不成立，schema 可能需要改為要求轉錄時標註，而那是破壞性變更，必須在凍結前發現。

此功能的價值超過其餘所有功能總和。原始 PDF 最大的閱讀障礙即為符號查找，解決此點即達成專案主要目標的大半。

**F2　雙向交叉追溯**
任一符號可查詢「於何處定義」與「被哪些公式使用」。此關係由 `lhs`/`rhs` 欄位自動推導，不需額外標註工作。

**F3　原文掃描對照**
每條公式旁提供切換鈕，展開原始掃描片段。有 bbox 者裁切顯示並提供「檢視整頁」；無 bbox 者直接顯示整頁（見 5.3）。由於本專案排除數值驗證，此功能是唯一的錯誤防線，不得省略。

**F4　全文檢索**
單頁應用採 hash 路由時，瀏覽器原生 Ctrl+F 僅能搜尋當前渲染內容。站內檢索因此不是加分項而是必要功能，須於第一個里程碑即納入。檢索須同時涵蓋中英兩種語言的敘述欄位。

**索引產生方式。** 全站檢索需涵蓋全部章節，與 4.3 提及的「分章延遲載入」直接衝突——要能搜尋，就得先載入全部文字。解法是**由離線腳本產生 `generated/search-index.json` 並 commit**，前端只負責載入既成索引。

此作法不違反 4.3 的設計意圖：該節的目的是讓貢獻者「新增內容不需執行任何指令，commit 即生效」，而索引可由 CI 定期重建，貢獻者的工作流程完全不變。同一模式亦適用於 9.2 的檢查結果輸出。

**F5　譯註視覺區隔**
中文譯註以明顯不同的樣式呈現（如左側灰底區塊），並標示為「譯註」。原文與譯註在資料層與視覺層均須嚴格分離（見 5.7）。

**F6　語言模式切換**
提供 EN only / ZH only / 對照 三種模式（見 5.7.3），設定持久保存於 localStorage。

### 6.2 次要功能

- F7　模組相依關係圖（可過濾、可聚焦子圖）
- F8　資料表排序與曲線繪製
- F9　深層連結（每條公式具永久 URL）
- F10　行動裝置適配
- F11　轉錄狀態視覺化（draft / reviewed / verified 於介面上可辨識；並依 `issues` 型別分類顯示，見 5.3.3）
- F12　進度呈現（依 `coverage.yaml` 顯示已處理頁數比例，見 5.9）
- F13　原文未定義符號清單（自 `source: inferred` 與 `undefined_in_source` 自動彙整，見 2.4）

## 7. 技術選型

### 7.1 前端（線上）

| 用途 | 選擇 | 理由 |
|---|---|---|
| 應用框架 | 原生 ES modules，不使用框架 | 內容驅動型網站，React 等框架僅增加負擔 |
| 數學排版 | KaTeX（CDN） | 數百條公式時效能顯著優於 MathJax |
| YAML 解析 | js-yaml（CDN） | 免除建置流程的關鍵 |
| 全文檢索 | MiniSearch | 支援載入預先產生之索引（見 6.1 F4），避免瀏覽器端重建 |
| 關係圖 | Cytoscape.js | 節點過百時支援過濾與子圖聚焦，優於 Mermaid |
| 圖表 | 手寫 SVG 或 uPlot | 避免為少量圖表引入 Plotly 等重量級函式庫 |
| 影像格式 | WebP | 掃描件壓縮率佳，全瀏覽器支援 |
| 部署 | GitHub Pages | 純靜態；repo 本身即為協作介面 |

**「純前端」的界線（v1.2 釐清）**

此限制的目的是保障**貢獻者的工作流程**：新增內容不需安裝工具、不需執行指令，commit 即生效。它不禁止 repo 中存在由離線腳本產生的檔案。

因此 `generated/` 下的檢索索引（6.1 F4）與檢查結果（9.2）皆屬合規——它們由 CI 在 push 後重建，貢獻者無須感知其存在。前端本身仍為純靜態，不需任何建置步驟即可執行。

KaTeX 須開啟 `trust` 選項以允許 `\htmlData`（見 6.1 F1）。由於全部輸入皆來自本 repo 之資料檔而非使用者輸入，此設定不引入注入風險。

### 7.2 轉錄工具鏈（離線，可全本地執行）

前端的「純前端」限制僅適用於網站本身；轉錄階段的工具不受此限，且**建議採本地方案**以控制成本並保有可重複執行的批次流程。

#### 7.2.1 建議管線

```
整頁影像
  └─▶ 版面偵測 ──▶ 區塊分類 + bbox 座標
        ├─ 公式區 ──▶ 公式辨識 ──▶ LaTeX
        ├─ 文字區 ──▶ OCR      ──▶ 純文字
        └─ 表格區 ──▶ 表格辨識 ──▶ CSV
                          ↓
                    組裝為 YAML
```

**此管線的關鍵附加價值：版面偵測工具直接輸出區塊 bbox 座標**，正是 5.3 節所需的欄位。此舉使 bbox 成為 OCR 的副產品而非額外工時，是該欄位得以保留於 schema 的前提。

#### 7.2.2 候選工具

| 工具 | 用途 | 運行條件 | 備註 |
|---|---|---|---|
| Surya | 版面偵測 + OCR + 表格辨識 | 本地，GPU 佳 | 輸出含 bbox，管線核心 |
| Marker | 上述之整合封裝（PDF → Markdown） | 本地 | 建議先試，可省整合工 |
| pix2tex (LaTeX-OCR) | 公式圖 → LaTeX | 本地，CPU 可跑 | 輕量 |
| Texify | 公式圖 → LaTeX | 本地，需 GPU | 通常較 pix2tex 準確 |
| img2table / PPStructure | 表格辨識 → CSV | 本地 | 附錄表格用 |
| Tesseract | 純文字 OCR 備援 | 本地，CPU | 數學表現差，僅供文字段落 |
| Qwen2.5-VL / InternVL | 本地 VLM，可直接輸出 YAML | 本地，7B 約需 12–16 GB VRAM | 見下方風險 |

#### 7.2.3 本地 VLM 的特殊風險

本地視覺語言模型可直接以 prompt 指定輸出符合本文 schema 的 YAML，省去組裝程式，具吸引力。但存在**幻覺風險**：模型會對辨識不清的符號進行「補全」，產生語法正確、外觀合理但內容錯誤的輸出。

由於本專案排除數值驗證（見 2.3），此類錯誤缺乏自動偵測手段。若採用 VLM，必須：

- 一律標記 `status: draft`，不得直接標為 reviewed
- 逐條與掃描原文目視核對後方可升級狀態
- 對量綱檢查未通過者優先複核

#### 7.2.4 建議執行方式

以本地管線跑第一輪，取得 bbox 與初稿；公式密集或辨識信心低的頁面，再以雲端視覺模型複核第二輪。1988 年掃描件對所有工具均構成挑戰，M0 抽樣測試將揭示實際落差。

## 8. 執行階段與里程碑

### M0　文件取得與盤點

**工作項目**
- 取得 CR-166536 完整 PDF；因超過常見上傳限制，須以 `qpdf` 或 `pdftk` 拆分為每 50 頁一份
- 以 `pdffonts` 確認是否存在文字層（1988 年文件多為純掃描）
- 取得姊妹文件 **CR-166535**《Generic Tilt-Rotor Simulation User's and Programmer's Guide》，作為模組串聯關係的權威來源
- 取得 **CR-166537**《Development and Validation》，作為背景參考
- 抽樣 10 頁進行 OCR 測試，測定實際準確率；同時評估 7.2 節管線是否能自動輸出可用的 bbox
- 確認附錄頁碼編碼形式（`A-1` 或其他），據以填寫 5.2 節之 `page_map`
- 統計章節數、公式數、圖表數，並區分附錄中常數表／查表／曲線圖之比例
- **決定掃描影像處理參數並回填 5.8.7 節**（畫質、DPI、是否二值化）。抽樣時應以不同參數各轉一份比較 OCR 結果與目視品質

**完成判準**　產出工時估算所需之全部量化資料，且 5.8.7 節之影像規格已定案。**在此欄位填妥前不得開始批次轉檔。**

### M1　Walking Skeleton

**工作項目**
僅納入**單一章節**的內容，但渲染層功能全數開啟（F1–F6）。外殼層僅需最簡首頁（章節列表加檢索框）。

**章節選擇原則**　選擇中等難度章節（如運動方程或機翼），不選最簡單者。目的是在小範圍內踩完工具鏈的全部坑洞。

**先行驗證項目（排序在其他工作之前）**

1. **F1 的符號標註路徑**（見 6.1）。此為最高優先功能且屬凍結範圍；若字串取代方案不成立，schema 可能須改為要求轉錄時手動標註，而該變更為破壞性，必須在凍結前發現。
2. **schema 壓力測試**（見 4.2.3）。額外抽取 3–5 頁旋翼與飛行控制章節的公式灌入 schema，僅驗證表達力、不做完整轉錄。重點檢查分段／條件式、方程組、矩陣式、跨頁續行式、改寫關係。

**完成判準**　該章可完整閱讀、符號可查（含常數值顯示）、掃描可對照、檢索可用、語言可切換；上述兩項先行驗證通過；且 **schema 與渲染層對外介面自此凍結**。渲染層程式碼仍可增補（如 F8），外殼層與首頁不在凍結範圍內（見 4.2.1）。

### M2　基礎字典建置

**前提事實**　原文**沒有**全書統一的符號表，而是各 subsystem 章節各附一份。本里程碑的範圍據此界定。

**工作項目**
- 掃描**各 subsystem 的符號表頁面**（一章約一頁），建立 `symbols.yaml` 骨架，`scope` 直接取 subsystem id
- 產出**跨 subsystem 重名衝突清單**，裁定哪些符號歸入 `scope: global`
- 依 5.4.2 之命名規約產生 key，並實作參照完整性檢查腳本（見 9.2）
- 完成 `constants.yaml`（附錄常數表，成本低且可立即提升 F1 價值）
- 完成 `toc.yaml` 章節樹
- 完成 `page_map` 頁碼對照，涵蓋前言、正文、各附錄

**為何仍應先做，而非逐章補**　符號表頁本身頁數極少、成本極低，但**只有先掃過全部 subsystem 的符號表，才能發現跨章重名衝突**，而重名衝突正是決定 key 命名策略與 scope 解析規則的前提。若改為逐章補建，很可能到第四章才發現 `T` 撞名，屆時前三章的 key 已經定型。

**明確不追求完整**　正文中出現但 subsystem 符號表未列的符號必然存在（原文變數定義不全，見 2.4），這些留待 M3 逐章補入，並依 5.4.3 標記 `source: inline` 或 `inferred`。

**完成判準**　各 subsystem 符號表頁已全數掃錄、跨章重名衝突已裁定、`global` 名單已定、參照完整性檢查可執行。**不以「符號表完整」為判準**——該目標在讀完全本前不可能達成。

### M3　逐章轉錄（主要工時）

**建議順序**
1. 運動方程與座標系統
2. 機身、水平尾翼、垂直尾翼（結構單純，建立流程信心）
3. 機翼（含旋翼尾流沉浸面積模型）
4. 旋翼（最複雜，留待流程成熟後處理）
5. 飛行控制、混控邏輯、短艙傾轉排程
6. 引擎、調速器、傳動系統
7. 起落架與地面效應

**產出**　每章一個 `equations/*.yaml` 檔案，可獨立上線。

### M4　附錄資料表

依第 10 節之分級策略處理。

### M5　模組相依關係圖

須待全部章節完成後執行，因跨模組耦合（旋翼尾流對機翼、機翼下洗對尾翼）須待資料齊備方能正確描繪。

**呈現層次**
- 頂層：各氣動模組 → 力與力矩合成 → 六自由度運動方程
- 干擾路徑：旋翼尾流對機翼、機翼下洗對尾翼——傾轉旋翼模型最關鍵且最易被忽略的耦合
- 控制路徑：駕駛桿輸入 → 混控與轉換排程 → 各操縱面與旋翼控制

### M6　校對與發布

全本交叉校對，處理 `issues` 欄位累積之待決事項，正式發布。

## 9. 品質保證

### 9.1 限制條件

專案排除模擬器實作，因此無法採用「跑出正確配平即證明轉錄正確」的驗證途徑。品保機制必須完全由文件內部提供。

### 9.2 三層防線

**第一層：參照完整性檢查（自動）**

離線腳本檢驗資料層的內部一致性，結果輸出至 `generated/checks.json` 供介面顯示：

- 每條公式 `lhs` / `rhs` / `condition_symbols` 中的每個 key，必須能依 5.4.1 之解析規則在 `symbols.yaml` 中找到
- `id` 全域唯一；`relates_to.target`、`group.id`、`defined_in` 所指對象必須存在
- `pdf_page` 落在 `page_map` 涵蓋範圍內；`printed_page` 為字串型別
- `status` 與 `issues` 之值屬於允許集合

此檢查**恰好攔截 5.4 節警告的失效模式**：OCR 將 `α` 誤判為 `a` 時，`a` 不存在於符號字典，腳本立即報錯。它不需要任何量綱資料，實作規模約數十行，是本專案 CP 值最高的自動檢查。

（v1.1 稱量綱檢查為「唯一可自動化的正確性檢查」，該敘述有誤——參照完整性檢查更便宜且更有效。）

**第二層：原文對照（F3）**
每條公式均可一鍵展開原始掃描。此設計使錯誤能被讀者發現並回報，而非成為永久性的靜默錯誤。這是本專案品保的核心。

**第三層：狀態標記與問題追蹤**
每條公式標記 `status`（draft / reviewed / verified）與 `issues` 清單。網站上以視覺方式呈現狀態，讀者可清楚知道哪些內容尚未經過複核。升級判準見 9.5。

### 9.2.1 量綱一致性檢查（選配，暫不實作）

量綱檢查在 v1.1 列為第一層防線，v1.2 降為選配，理由是：**9.5 的狀態升級機制要求所有內容經人眼逐字核對，而量綱檢查能抓到的錯誤，逐字核對本來就會抓到。** 它只是一張較快、較廉價的第二層網，而其成本並不低——需為數百個符號填寫 `dimension`、撰寫 LaTeX 剖析腳本、處理假陽性。

須釐清一點：**此檢查稽核的對象是本專案的轉錄品質，不是 Ferguson 的原文。** 量綱對不上時，絕大多數情形是轉錄時漏了一個 ρ 或誤讀了符號，而非原文推導有誤。

若日後決定實作，路徑如下：

1. `symbols.yaml` 之 `dimension` 欄位須填寫（見 5.4.4）
2. 以 `sympy.parsing.latex.parse_latex` 將 `latex` 轉為語法樹，不自行撰寫剖析器
3. 遍歷規則：`+ - =` 兩側量綱須相同（主要抓錯來源）；`× ÷` 指數相加減；`^n` 之 n 須為數值常數，否則跳過；`sin`／`cos`／`exp`／`log` 引數須無因次
4. 輸出三態 `pass | fail | skipped`，**且 skipped 必須顯示於介面**。若僅標示 fail，讀者會將「沒有紅字」誤讀為「已檢查通過」，此防線反而製造虛假信心
5. 1988 年工程式常內嵌帶單位的經驗常數（如將 deg→rad 換算揉入係數），會產生假陽性，需人工豁免：

```yaml
  dimensional_check: skip
  dimensional_check_reason: "式中 0.0698 內含 deg→rad 換算"
```

**務實預期**：可自動檢查的比例約三至五成，其餘因矩陣式、未知符號、內嵌常數而跳過。建議待 M3 完成一至二章、實際觀察 OCR 錯誤型態後再決定是否投入；若人眼核對已足敷所需，可永不實作。`dimension` 欄位則先行保留。

### 9.3 資料表專用檢查

數值表格的 OCR 錯誤（8 與 3、5 與 6、小數點位置）幾乎無法以肉眼掃視發現。轉錄完成後須執行：
- 列和／行和交叉檢驗
- 與同頁其他數據組的一致性比對
- 明顯離群值標記

### 9.4 原文與譯註分離原則

中文內容僅得存放於 `text.zh`（該段原文之對譯）或 `notes/zh-TW/`（譯者補充說明），兩者分工見 5.7.2，**嚴禁寫入 `latex`、`text.en` 或 `note` 欄位**。專案跨度數月，若兩者混雜，後期將無法區分何者為 Ferguson 原文、何者為當時的推測。

譯註於介面上須有明確視覺標記（F5），使讀者不致將譯者詮釋誤認為原作者陳述。

### 9.5 狀態升級判準

**通則：一切機器產出一律標記 `status: draft`，無論來自 OCR、公式辨識或視覺語言模型。** 唯有經人工核對後方可升級。v1.1 僅對 VLM 設此限制，v1.2 擴及全部自動化工具——OCR 對 1988 年掃描件的誤判同樣不會自我聲明。

三態需有可驗證的判準，否則將退化為主觀標記：

| 狀態 | 判準 |
|---|---|
| `draft` | 機器輸出，尚未經人眼核對 |
| `reviewed` | 已逐字對照掃描原文核對一次 |
| `verified` | `reviewed` + 參照完整性檢查全數通過 + 無未決 `issues` |

`verified` 刻意不定義為「經第二人複核」。在單人或小團隊專案中，該定義將使此狀態永遠無法達成，反而使狀態機制失去意義；綁定於自動檢查較為務實。

VLM 的幻覺產出語法正確、外觀合理，在缺乏數值驗證的前提下難以事後發現，故其 `draft → reviewed` 的核對尤其不得跳過（見 7.2.3）。

### 9.6 中譯品質規範

- 術語首次出現須併列英文原文（見 5.7.4）
- 譯註不得補充原文未載之推導或結論；如需補充，明確標示為「譯者補充」
- 對原文語意不明處，譯註應據實記錄不確定性，不作臆測性補全

## 10. 附錄資料處理策略

附錄為全本數位化中最容易低估的部分。內容可分三類，處理成本差距顯著：

| 類型 | 存放 | 處理方式 | 成本 | 策略 |
|---|---|---|---|---|
| 常數表（幾何、慣量、重量） | `constants.yaml` | OCR → 鍵值對 | 低 | 全數處理，優先於 M2 完成 |
| 多維氣動係數查表 | `tables/*.csv` | OCR → CSV + 曲線渲染 | 中 | 全數處理 |
| 曲線圖（僅有圖形，無數值） | `scans/` | 保存掃描影像 | 低 | **預設僅存圖** |
| 曲線圖（關鍵者） | `tables/*.csv` | WebPlotDigitizer 數化 | 高 | 選擇性處理 |

**常數表優先。** 常數表成本最低，卻能立即提升符號提示（F1）的價值——讀者查詢符號時同時看到數值，附錄與正文因而串接。建議於 M2 階段即完成，不必等到 M4。

**關鍵決策：曲線圖預設不數化。** 僅當某曲線對理解模型具決定性意義時（例如轉換走廊邊界、旋翼尾流沉浸面積係數、下洗角變化）才投入數化工時。全本硬性數化曲線是此類專案最常見的爛尾原因。

## 12. 工時估算

以 300 頁、預估 200–500 條公式計：

| 項目 | 估計工時 |
|---|---|
| M0 盤點 | 4–8 h |
| M1 Walking Skeleton（含渲染層開發） | 16–24 h |
| M2 基礎字典（含 constants.yaml） | 10–16 h |
| M3 逐章轉錄（英文原文） | 30–50 h |
| M4 附錄資料表 | 8–16 h |
| M5 相依關係圖 | 4–8 h |
| M6 校對發布 | 8–12 h |
| **小計（不含中譯）** | **約 80–134 h** |
| M3′ 中文譯註（選配） | 25–40 h |
| **合計（含中譯）** | **約 105–174 h** |

公式密集章節約每頁 10–20 分鐘，含 OCR 校對；bbox 若由管線自動產生則不計工時，若需人工標註另加 8–10 h。

**上表應視為樂觀情境。** 未納入者包括：7.2 管線的建置與調校（工具安裝、GPU 環境、組裝為 YAML 的膠水程式）、參照完整性檢查與索引產生腳本、影像批次轉檔與逐頁目視抽檢、`issues` 之後續處理。此外 M3 的 30–50 h 攤至約 240 頁本文為每頁 7.5–12.5 分鐘，已抵在上述 10–20 分鐘區間的下緣。實際投入時數高於本表屬正常情形，不影響專案可行性——解耦架構確保任何時點停工皆有可用成果（R2）。

**中譯應視為獨立軌道。** 譯註為選填欄位，網站在僅有英文的情況下即可正常運作並發布。建議先完成全本英文轉錄，中譯隨後逐章補入，避免翻譯進度拖累主線。

以業餘時間推進（每週 6–10 小時），不含中譯之完整專案預期為 **三至五個月**。M1 與 M2 完成後（約 30 小時），即具備可對外展示的成果。
